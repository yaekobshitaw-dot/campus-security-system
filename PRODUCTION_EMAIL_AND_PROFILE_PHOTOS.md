# Production Email and Profile Photos

## Gmail API Email

The active backend implementation uses the Gmail REST API and OAuth 2.0 refresh-token grant (`backend/src/services/emailService.js`). It does not use Nodemailer/SMTP for production email. `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are separate credentials used by the application's Google sign-in flow; they do not configure the Gmail sender.

Set these variables on the Railway backend service:

| Variable | Purpose | Source |
| --- | --- | --- |
| `GMAIL_CLIENT_ID` | OAuth client identifier used for Gmail token exchange | Google Cloud Console OAuth client |
| `GMAIL_CLIENT_SECRET` | Secret for that OAuth client | Google Cloud Console OAuth client; keep only in Railway secrets |
| `GMAIL_REFRESH_TOKEN` | Long-lived authorization for the sender account; exchanged for a fresh access token on every send | Generated by authorizing the sender account with the same client and Gmail scope |
| `GMAIL_SENDER` | Explicit From address and the only recipient of the self-test | Authorized Gmail mailbox or a configured Gmail send-as alias |

All four values are required. The backend does not persist or cache access tokens, does not expect Google to return a replacement refresh token during refresh, and never stores OAuth credentials in the database. An expired access token alone is recoverable by another refresh exchange. `invalid_grant` means Google rejected the refresh grant; common causes include revocation, an expired testing-mode grant, or a token generated for a different OAuth client.

### OAuth Setup and Reauthorization

1. In Google Cloud Console, select the project that owns the OAuth client, enable the Gmail API, and configure the OAuth consent screen for the sender account's organization/audience. Configure the consent-screen app name, support email, authorized domain(s), and verification/publishing state required for the selected audience and Gmail scope. An External app left in Testing can have refresh tokens expire after seven days.
2. Use the same OAuth client for initial authorization and refresh-token exchange. If using Google's OAuth 2.0 Playground to obtain a token, configure the client as a Web application and add `https://developers.google.com/oauthplayground` as an authorized redirect URI; enable the Playground option to use your own OAuth credentials.
3. Authorize the Gmail scope `https://www.googleapis.com/auth/gmail.send` as the sender mailbox, exchange the authorization code for tokens, and copy only the returned refresh token into Railway's `GMAIL_REFRESH_TOKEN`. Do not paste credentials into this repository, logs, issues, or chat.
4. Set `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_REFRESH_TOKEN`, and `GMAIL_SENDER` in Railway's backend service variables, then redeploy/restart that service. Check the authenticated `GET /api/email/diagnostic` endpoint as an admin. To actually send a fixed test message only to `GMAIL_SENDER`, send an authenticated admin `POST /api/email/diagnostic/test` with JSON `{ "confirmation": "SEND_TO_CONFIGURED_SENDER" }`.

The diagnostic GET only exchanges a token; it sends no email. The POST test cannot accept an arbitrary recipient. Logs and API errors intentionally omit provider response bodies, message contents, recipients, and credentials. If reauthorization still reports `invalid_grant`, verify that the refresh token and client ID/secret are a matching set and that consent is no longer subject to Testing-mode expiry. Confirm the sender address/alias is permitted by Gmail.

The repository does not contain a Gmail OAuth callback or token database. Reauthorization is therefore an operator action in Google Cloud/OAuth Playground followed by updating Railway variables. No production OAuth redirect URL is assumed by the backend's Gmail integration. If an application-owned OAuth flow is adopted later, add its exact deployed callback URI to the OAuth client's authorized redirect URIs before using it.

## Profile Photos

Uploads are validated by Multer (JPEG, PNG, WebP, or GIF, one file, maximum 5 MiB), written to `PROFILE_PHOTO_STORAGE_DIR`, persisted in `users.profile_photo_url`, and served publicly by Express at `/uploads/profile-photos/<filename>`. The upload and static-serving directory are currently the same. The URL uses the request's forwarded protocol and host, so it points directly to the backend and works for Vercel and mobile clients configured with the Railway backend URL. The existing dashboard/mobile image components fall back when the image fails to load.

The default directory is `backend/uploads/profile-photos`, which is local container storage. The repository has no object-storage adapter or Railway volume declaration. On Railway, local files are not a persistence guarantee across redeployments/restarts, and a database URL can remain after its corresponding file has disappeared; that produces a 404 even though the URL and Express static route are correct.

For the existing architecture, attach a Railway persistent volume to the backend service, mount it at `/data`, and set `PROFILE_PHOTO_STORAGE_DIR=/data/profile-photos`. Ensure the backend process can create, read, and delete files in that mount. Redeploy only after copying recoverable existing files into the mounted directory while preserving their filenames. Do not delete the old directory until representative URLs return 200 from the deployed backend and backups are verified. The repository cannot recover files already lost from ephemeral storage; restore them from backup or ask users to upload again.

Ensure every backend process that serves a photo sees the same files. A single attached volume is suitable for a single backend instance; if the deployment requires multiple independent replicas or shared access beyond that volume, use a supported shared object-storage integration and migrate existing files/URLs deliberately. No external storage service is configured or silently introduced here. Configure backups for the volume and monitor photo GETs after deployment.
